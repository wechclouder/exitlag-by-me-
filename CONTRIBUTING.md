# Разработка wetwiLAG

Спасибо за помощь с развитием проекта. Обсуждайте изменения через Issues, а готовые предложения отправляйте через Pull Request в `main`.

## Требования

- Windows 10/11 x64.
- .NET 10 SDK.
- Для запуска WPF-приложения — Windows Desktop Runtime .NET 10; автономная публикация включает необходимый runtime.

## Сборка и проверки

```powershell
dotnet restore .\wetwiLAG.sln
dotnet build .\wetwiLAG.sln --configuration Release
dotnet run --project .\Tests\wetwiLAG.SmokeTests.csproj --configuration Release
```

Для самостоятельного исполняемого Windows x64 приложения:

```powershell
dotnet publish .\wetwiLAG.csproj --configuration Release --runtime win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -p:DebugType=none -p:DebugSymbols=false -o .\publish\win-x64
```

Pull Request проходит Release-сборку, read-only smoke-проверки и публикацию Windows x64 артефакта на GitHub Actions для Windows.

## Соглашения проекта

- Сначала проверьте реальное значение из Windows/сети. Не подставляйте примерные или случайно сгенерированные измерения; отсутствие данных обозначайте явно.
- Сетевые запросы должны быть асинхронными, иметь тайм-аут, принимать `CancellationToken` там, где операция продолжительная, и корректно обрабатывать отсутствие ответа.
- Изменения системной конфигурации допустимы только через документированный безопасный Optimizer workflow: отдельное понятное подтверждение, неизменяемая резервная копия **до** изменения, проверка результата и проверенный откат.
- Не добавляйте изменения реестра, обход защиты, вмешательство в игровую сеть или файлы, автоматическую смену MTU/IPv6, скрытое повышение прав или гарантии улучшения пинга.
- Профили и настройки UI не должны неявно изменять параметры Windows.
- Для UI используйте существующую архитектуру WPF/MVVM, observable models и `RelayCommand` / `AsyncRelayCommand`.
- При изменении observable-свойства, команд, XAML bindings или отмены проверяйте работу интерфейса при запуске опубликованного приложения, а не только успешную компиляцию.
- Прежде чем тестировать изменение DNS, схемы электропитания или параметров адаптера на реальной системе, попросите отдельное явно выраженное подтверждение и обеспечьте проверенный план отката. Автоматизированные проверки должны оставаться безопасными и read-only.

## Что проверяет текущий smoke-тест

Консольная программа в `Tests/` проверяет валидацию адресов и DNS, сериализацию пользовательских настроек, профилей и истории, отсутствие перезаписи исходных backup-файлов, перечисление сетевых адаптеров Windows, чтение состояния DNS и схемы электропитания, а также реальные loopback DNS/ping/traceroute запросы и обработку тестовой недоступной сети.

Smoke-тест намеренно **не** применяет системные изменения. Перед изменением сетевого привилегированного кода добавляйте дополнительные проверки отката; ручные проверки на отдельной тестовой Windows-системе должны быть документированы в описании Pull Request.
